# CMS category-type filtering follows the category link, not the place type

Both CMS forms submit the canonical type **code** with a native `GET`: `Attractions` is `attraction`. The current Categories controller accepts that known scalar and adds `ct.code = selectedType`; therefore `/admin/categories?type=attraction` cannot return `hotel_resort`, `restaurant`, or `theater` categories under the inspected source. The Places controller has a separate **confirmed** regression: it filters through the linked category's type while displaying the place's own `p.type`, allowing the selected-label/data mismatch and excluding uncategorized places. The current diff also contains dead native-filter initialization and no behavioral filter coverage.

**Watch for:** **confirmed** — changing selected-option rendering cannot repair the server result set. Categories has only one predicate-dropping branch (an absent, non-scalar, or unrecognised query value); Places must filter `p.type`, not the linked category's type.

**Verdict**: NEEDS_CHANGES

## High-level view

`category_types.code` is the source of truth from migration and seed data through the form options and controller validation. For valid `type=attraction`, Categories joins `c.type` to `ct.code` and constrains `ct.code` to `attraction`; with the foreign key, this is exactly `c.type = 'attraction'`. **confirmed** — the all-category result is possible only when `selectedType` is empty.

Places diverged in the uncommitted diff: its selected type follows `p.category_id -> c.type -> ct.code`, but the schema and list display use the independently stored `p.type`. **confirmed** — a restaurant attached to an attraction category appears under Attractions while still being labelled restaurant.

Native filters are deliberately excluded from WebAwesome replacement. The added initializer requires `data-selected-type`, which neither filter has, so it cannot alter state or predicates; **confirmed** — it is dead code, not the cause of an all-row query.

## Canonical values survive from the database to the form

`database/migrations/1760000000004_create_category_types.ts:5-22` makes `category_types.code` the primary key and seeds `attraction`, `restaurant`, `hotel_resort`, and `theater`. `database/migrations/1760000000005_link_category_types.ts:5-11` makes both `categories.type` and `places.type` foreign keys to that code. `database/seeders/demo_seeder.ts:77-145` uses the same codes for the four types, categories, and each place's explicit `type`.

`app/services/category_type_service.ts:16-18` supplies those rows to both filters. `resources/views/admin/categories/index.edge:6-10` and `resources/views/admin/places/index.edge:6-10` render `type.code` as the `name="type"` option value and `type.name_en` as its label. Thus selecting Attractions submits `type=attraction`, not `type=Attractions`. `start/routes.ts:33,44` route those GETs to the reviewed admin page controllers; there is no competing admin GET route.

## Categories can be unfiltered only when its accepted query is empty

At `app/controllers/admin/categories_controller.ts:9-14`, `request.qs().type` survives only if it is a string equal to one of the database codes. Missing input, repeated input parsed as non-scalar, or an unknown code produces `selectedType = ''`; a valid `attraction` remains `attraction`.

The query joins `categories as c` to `category_types as ct` by `ct.code = c.type` at lines 15-18 and adds `where ct.code = selectedType` at lines 35-37. **confirmed** — with `selectedType = 'attraction'`, all returned rows must have `c.type = 'attraction'`; the reported mixed eight-row Categories set cannot be generated by this controller for that accepted query. The decisive diagnostic is the URL/value at the controller boundary, not another selected-state patch. The existing compiled controller and template under `build/` have the same filter code, so this is not an unbuilt-source finding.

The smallest Categories hardening is to retain validation but spell the predicate as `query.where('c.type', selectedType)`. This clarifies the listed table but deliberately does not conceal an empty `selectedType`; the regression test must establish that the GET parameter arrives as expected.

## Places selects on one type and displays another

The current diff changed `app/controllers/admin/places_controller.ts:25-35` from filtering `p.type` to joining `p.category_id -> c.id`, then `c.type -> ct.code`, and filtering `ct.code`. Its projection at line 32 and `resources/views/admin/places/index.edge:29` still show `p.type`.

```
selected type=attraction
current filter: p.category_id -> c.type -> ct.code = attraction
listed value:    p.type
required filter: p.type = attraction
```

**confirmed** — a place with `p.type = 'restaurant'` and an attraction category is included for Attractions and labelled restaurant. Because `places.category_id` is nullable (`database/migrations/1760000000002_create_content_tables.ts:46-77`), the new inner joins also remove uncategorized places from both filtered and All views. The definitive minimal patch removes those two joins and uses `query.where('p.type', selectedType)`; the translation join remains necessary.

## Native control behavior lacks a regression proof

The filters use `data-native-filter`, while `resources/js/admin_components.js:76-96` transforms only `select:not([data-native-filter])`; their inline submit handlers therefore submit the native `type` value. The loop at lines 11-15 targets `select[data-native-filter][data-selected-type]`, but neither template provides that second attribute. **confirmed** — it runs on no element and cannot drop a database predicate.

`tests/functional/cms_pages.spec.ts:9-71` seeds only one type/category and only checks that CMS pages return 200. **Not tested:** selected markup; exclusion of another category type; filtering Places by `p.type`; the mismatched legacy category/place case; and uncategorized Places. These tests are needed to prevent another display-only fix from masking a server-query regression.
