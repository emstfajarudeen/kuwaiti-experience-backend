# App 2 Figma screen audit

Source: [Kuwaitiexperience, App 2 page](https://www.figma.com/design/Ut5EtFQuXCwoux1QMCSZDD/Kuwaitiexperience?node-id=625-13471) (`625:13471`). Reviewed 20 October 2026. The page contains **81 top-level mobile frames**. I read the text content of every frame and visually inspected representative screens across the main flows. The page has no wired prototype reactions, so navigation order below is inferred from canvas adjacency and visible controls; it is not a verified prototype flow.

## Product model shown by the designs

The app combines a Kuwait discovery guide with two transactional transport products: on-demand/scheduled cab rides and car rentals. A short-form Explore video feed, saved content/addresses, phone-based accounts, booking history, ratings, and support surround those core flows. Home links into cab, rental, discovery categories, and video. The designs are significantly broader than the existing website/API implementation.

## Important design inconsistencies and unresolved rules

- **Privacy/terms text is unrelated placeholder content.** The frames mention “Gheyar Seller App,” sellers/buyers, bank details and Al Rajhi Bank/Stripe. Do not publish or treat that copy as the Kuwait app's policy. Legal content needs approved text.
- **Example bookings disagree with each other.** Dates, references, prices and payment states vary across adjacent frames. Rental cards show different day/total values; some rent cards reuse a `CB–KWT` cab-style reference. Treat these as visual examples and define calculation/reference/status rules in the backend contract.
- **Cab pricing/payment semantics are unknown.** A quote screen shows KWD 2/4/6 by class, while a completed trip shows KWD 6.750. Define estimated versus final fare, taxes/fees, authorization, capture, cancellation charge and cash collection with the operator/payment provider.
- **Rental booking fee versus rental amount is explicit but operationally incomplete.** The mock says the rental amount is paid directly to the provider and the app charges only a KWD 3 booking fee. Confirm whether that is a fixed fee, refundable, subject to tax and sufficient to reserve inventory.
- **Live integrations are not identified.** Map/geocoding/routing, OTP/SMS, dispatch/driver tracking, payment gateway, rental company inventory and theater showtimes need product/vendor decisions. The designs do not specify APIs, credentials or service-level behavior.
- **Guest permissions are not shown.** Define which actions require login (booking, saving, commenting, reporting, contact) and whether guest state is retained after account creation.
- **Search, notification icon and “Schedule” are visible but lack destination/result screens.** Keep them as open requirements rather than inventing endpoints or claiming a complete flow.
- **Explore moderation needs policy.** The report reasons are visible; queue handling, review decisions, user sanctions, comment deletion and appeal behavior are not.
- **Theater “Active Movies” and showtimes appear editorial.** There is no movie-ticket checkout in this page; the shown actions are Call and Book a Cab.
- **CMS is not designed in App 2.** Each new domain still needs an operator workflow for safe content, fleet, provider, booking, support and moderation management. Plan these alongside the matching app API section.

## Relationship to the current backend

Current AdonisJS/MySQL code supports public home/categories/places/pages, record-owned image delivery (`/api/v1/images/{key}`), a basic transport-location list and a WhatsApp enquiry URL, plus an admin CMS and admin JWT auth. It has no customer account, OTP, saved data, actual cab booking/dispatch/tracking, car-rental inventory/reservation/payment, unified booking history, video feed/social features, or support-submission storage. The [implementation plan](app2-api-implementation-plan.md) organizes these as separate approval-gated sections. The [API reference](app-api-reference.md) distinguishes live endpoints from proposed ones.
