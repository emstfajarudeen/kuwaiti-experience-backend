# CMS Tailwind migration guide

Status: implementation completed, 23 October 2026. All 11 sections have been implemented on `react-migration`. This guide remains the reference for the migration decisions and verification evidence; the current React + Inertia CMS is the reference implementation.

## Goal and boundaries

- Replace the CMS-owned styling in `resources/css/admin.css` with Tailwind utility classes in `inertia/`. Keep the current appearance closely matched; small visual differences can be corrected in later passes.
- Every existing control, action, validation message, menu, upload, editor, and flow must remain available and usable on desktop and mobile. Do not change server controllers, routes, field names, CSRF handling, redirects, auth, business rules, or public APIs for a styling task.
- Keep React + Inertia. `resources/views/inertia_layout.edge` is the active HTML shell and stays. The old `resources/views/admin/` templates are reference material, not active pages; deleting them is outside this styling migration.
- Tailwind should own CMS layout and component appearance when complete. Keep a small CSS layer for font imports, base styles, accessibility rules, animations or pseudo-elements that are clearer in CSS, and third-party Quill, FilePond, and Web Awesome integration. Do not claim that literally zero CSS remains.
- Do not restyle the 404/500 error pages accidentally: they currently load `resources/css/admin.css` and `resources/js/app.js`. Preserve their appearance or give them a separate stylesheet before removing shared legacy rules.

- 23 React page components, one shared layout, seven shared components: `inertia/pages/`, `inertia/layouts/admin_layout.tsx`, `inertia/components/`.

It retains brand/base styles, native control defaults, accessibility focus treatment, status/table pseudo-state rules, and Quill/FilePond/Web Awesome integration. Layout and most page/component presentation now use prefixed Tailwind utilities.
- Build entry: `vite.config.ts`; active CMS shell: `resources/views/inertia_layout.edge` loads `admin.css` and `inertia/app.tsx`.
- Baseline behavior: `docs/cms-parity-ledger.md`; browser tests: `tests/browser/`; functional tests: `tests/functional/`.
- React currently uses many semantic CSS class names and inline styles. Search before deleting a selector. Browser tests use `.notice-body`, `.rich-field`, `.ql-editor`, `.filepond--item`, and `#main-content`; retain these hooks or update tests to stable semantic/data hooks without weakening assertions.

## Migration method for every section

1. Read only the files listed for the section plus the matching rules in `admin.css`. Capture the current desktop (about 1440 px) and mobile (about 390 px) view for each touched screen, including relevant open menus, errors, and upload/editor states. Keep reference screenshots in a local artifact folder; do not replace the baseline with screenshots of the new styling.
2. Convert one component or page at a time. Preserve its JSX behavior, labels, `name` attributes, actions, method, accessibility attributes, state, and conditional rendering. Prefer complete, static Tailwind class strings or maps of complete strings; do not interpolate utility fragments such as `bg-${color}-600`.
3. Remove the corresponding legacy selector **only when** its last consumer has migrated. Legacy unlayered CSS can override layered Tailwind utilities even when the new stylesheet loads later; do not stack classes and assume order will fix a conflict. Check global element selectors too.
4. Check at desktop and mobile widths: all controls visible, reachable, correctly layered, and usable with pointer and keyboard. Confirm scrolling, fixed/sticky elements, focus states, validation feedback, dialogs, dropdowns, table overflow, Arabic text, and images.
5. Run `npm run typecheck`, `npm run lint`, `npm run build`, and the relevant existing browser scenario for changed screens. Run the full functional and browser suites at Section 11, or sooner if a shared component can affect unrelated screens. Do not add tests that merely repeat class names; add an interaction or visual check only for a real gap.
6. Record the section as done in this file with files changed, checks run, and any accepted small visual differences. Stop after the section and hand over a short summary before starting the next one.

## Tailwind setup details for Section 1

Use the current Tailwind CSS v4 Vite integration: install `tailwindcss` and `@tailwindcss/vite` as build dependencies, register `tailwindcss()` in `vite.config.ts`, and load one CMS Tailwind stylesheet from the Inertia shell. The official [Vite installation guide](https://tailwindcss.com/docs/installation/using-vite) is the source for the plugin setup. Use the `tw:` utility prefix from the start (for example, `tw:flex`) so Tailwind's generated utilities cannot collide with existing semantic CMS classes such as `hidden` or `border` while the old stylesheet is still present. Configure custom theme tokens without including the prefix in their names; Tailwind prefixes the emitted variables.

Add Tailwind incrementally. Its [Preflight reset](https://tailwindcss.com/docs/preflight) changes headings, borders, margins, and inputs globally, so initially import theme and utilities without Preflight, then decide at Section 11 whether to enable it after checking all screens and error pages. Restrict scanning to the React CMS source and verify generated utilities in the production build. Tailwind's [source detection guide](https://tailwindcss.com/docs/detecting-classes-in-source-files) explains explicit `@source` paths and why dynamic utility fragments fail.

Map existing `:root` colors, fonts, radii, and spacing in `admin.css` to a small `@theme` palette; avoid scattering new hard-coded colors throughout JSX. Keep the currently imported font files and third-party styles until their replacements are verified. Do not install a component library or change React page structure merely to adopt Tailwind.

## Verification and release rule

Run tests only against the isolated `kuwaitiexperience_test` database; `tests/bootstrap.ts` enforces this. Commands from the repository root:

```sh
npm run typecheck
npm run lint
npm run build
node ace test functional
CMS_BROWSER_EXECUTABLE='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' node ace test browser
git diff --check
```

The existing nine browser tests verify flows, not pixel parity across all 23 pages. Do representative desktop/mobile visual comparisons and manual control checks for each section; add focused browser checks for a discovered missing interaction. Do not delete the remaining shared/base or vendor CSS without replacing its behavior and checking error pages and editor/upload integrations. Section 11 implementation and automated regression gates are complete. Manual screenshot comparisons for every route and state remain a recommended visual QA follow-up; the automated browser suite does not prove pixel parity.
