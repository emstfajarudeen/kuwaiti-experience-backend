# CMS Ant Design forms and tables migration guide

Status: ready to implement, 23 October 2026. Work on the existing `react-migration` branch. This is a nine-section guide for a low reasoning coding model. Implement **one section per task**, record evidence below, and stop. The React + Inertia CMS is the behavior reference.

## Objective and limits

- Use Ant Design for CMS forms and the eight data tables. Keep every existing field, label, action, URL, filter, sort, page size, redirect, CSRF check, permission, upload, editor, and mobile control working. Minor visual differences are acceptable; missing behavior is not.
- Keep Adonis/Vine and the existing services as the source of truth for validation and business rules. Add client validation for clear, immediate feedback. Display server field errors beside the matching controls and non-field errors in the existing page notice.
- Keep Tailwind for page layout and branding. AntD owns migrated form and table controls. Keep Quill and FilePond for rich text and images; integrate them into forms without replacing their data contracts.
- Do not change public `/api/` routes or response formats for a CMS component migration. Do not remove the old Edge templates, existing tests, or shared CSS until their consumers are accounted for.
- The checkout already contains uncommitted React/Inertia/Tailwind work. Inspect status before editing, preserve that work, and do not reset or switch branches. Confirm `git branch --show-current` returns `react-migration` in every task.

## Rules for every section

1. Read only this guide, the section's files, their controller and validator, relevant routes, and relevant tests. Make a short checklist of current fields, `name` attributes, default values, submit intents, filters, actions, and failure behavior before editing.
2. Convert one screen at a time. Keep accessible labels and stable test selectors. Prefer AntD `Form.Item`, `Input`, `Select`, `InputNumber`, `Checkbox`, `Button`, and `Table` where they fit. Retain native hidden inputs, file inputs, and simple destructive POST forms when replacing them adds no validation value; style their visible buttons consistently.
3. Use the tested Section 1 submit adapter. AntD `Form` owns field values and invokes `onFinish`; it does **not** preserve native `onSubmit` behavior automatically. Set initial values through `initialValues`/`setFieldsValue`, not `defaultValue` inside a named `Form.Item`. Preserve exact wire names and encodings: `_csrf`, `intent`, `feature_ids[]`, `gallery[n][field]`, `place_hours[n][field]`, `on` checkboxes, local time strings, and multipart files.
4. Client rules should mirror required, length, format, and range constraints in Vine. Server validation is final. Map a server field path to the matching AntD `NamePath` and call `form.setFields` or show `Form.Item` help/error state. Keep a visible summary and focus/scroll to the first error. Never flash or log passwords. File fields cannot be repopulated after a failed redirect; keep the existing instruction to reselect images.
5. Keep server paging/filtering/sorting. Set AntD table `rowKey`, controlled pagination, and `onChange` to the existing URL query parameters. Do not paginate or sort only the rows already received from the server. Preserve row links, menus, confirmations, empty states, count text, and horizontal access to actions at about 390 px.
6. Use the current brand theme through `ConfigProvider` and explicit component tokens. Keep Tailwind utilities for layout. Avoid styling AntD's private DOM selectors. Check generated CSS order and SSR/hydration at a production build, including initial page paint.
7. Check desktop (about 1440 px) and mobile (about 390 px): empty/filled tables, invalid and successful form submissions, keyboard focus, error messages, menus, scroll, Arabic fields, and disabled/loading states. Add browser tests for behavior that the existing suite does not cover. Do not add tests that assert AntD class names.
8. Run the checks listed for the section. Update only that section's status row with files changed, test result, and known visual difference, then stop for review. Do not begin the next section in the same task.

## Submission and validation contract to establish in Section 1

- Create one small shared adapter for CMS mutation forms. It must submit `FormData` through the installed Inertia router to the current route, keep `_csrf`, preserve named submit-button `intent`, keep file values, disable repeat submissions, and preserve server redirect/success behavior. Prove it with a real low-risk form before using it elsewhere. If a particular auth/destructive flow requires a full page POST, keep that flow native and document the reason in its section.
- Do not infer wire names from AntD field names. Write a deliberate serializer for nested arrays and checkboxes. Test its output against the current controller input; avoid a general-purpose serializer that silently changes `on`, empty string, or `[]` semantics.
- Use the existing shared Inertia `errors` prop where automatic Vine validation supplies field errors. For controller `catch` blocks that swallow Vine errors, add a small safe mapping of validation messages into flashed field errors while retaining the current failure URL, generic notice for service errors, and flashed form data. Avoid editing the API exception response path.
- Make the adapter display server errors after redirect and keep entered values. A failed submit must not silently clear text, Arabic content, selected options, or dynamic rows. Never claim a client-only rule is a substitute for Vine validation.
- Verify AntD CSS-in-JS works with the existing SSR and Tailwind v4 layers. AntD documents `@layer theme, base, antd, components, utilities` when its `StyleProvider` layer mode is used. Use AntD's documented SSR style extraction or static style approach and verify no unstyled first paint or hydration warning. Do not add AntD's reset stylesheet without checking its effect on existing pages.

## Verification commands

Run from the repository root. Browser/functional tests use the isolated `kuwaitiexperience_test` database and must not be pointed at production data.

```sh
git branch --show-current
npm run typecheck
npm run lint
npm run build
node ace test functional
CMS_BROWSER_EXECUTABLE='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' node ace test browser
git diff --check
```

Run relevant browser and functional scenarios after each section; run both full suites in Section 9. A build alone does not prove SSR styling or form flow. Test initial production SSR HTML and hydration once AntD is introduced and again at the final gate.
